System purpose

DAAGS addresses a limitation of static public datasets in data analytics education by generating unique datasets that can change over time and respond to scenarios.

Generation pipeline

Existing datasets such as product data are used as references. Python generation logic combines those references with configurable weighted distributions to create new transactional records.

Current transaction model

Generated transaction records include transaction number, user ID, state, item count, product IDs, total amount, payment method, and timestamps.

Weighted generation

Regional and state behavior is represented through configurable weights. These distributions influence fields such as item counts, payment methods, and other generated behavior.

AI-assisted generation

Users can describe scenarios in natural language. The AI interprets the scenario and modifies generation weights rather than generating every record directly. This reduces the amount of LLM generation required.

Database architecture

PostgreSQL provides relational storage and transactional integrity. The architecture leaves room for indexing, scheduled generation, triggers, and deeper database integration as the project evolves.

Universal input direction

A major future direction is generic CSV input: analyzing columns, distributions, numerical patterns, and categorical frequencies instead of assuming a fixed retail schema.

Hardest technical problem

Column dependencies. Generating columns independently can create impossible relationships. Future work includes conditional distributions and dependency-aware generation.

Evolving data

The intended next stage is scheduled generation where datasets evolve over simulated time, including events, anomalies, peaks, valleys, and scenario-based changes.

Research finding

In one experiment, an AI-assisted scenario simulating a pandemic reduced overall sales in generated data by approximately 46% compared with the default configuration.

Problem

Reflections were collected in Google Sheets, which made organization, progress tracking, supervisor feedback, and long-term use difficult.

Role-based access

Four user levels, each seeing only what they need: Superuser (creates organizations), Administrator (manages supervisors), Supervisor (runs classes and reviews reflections), and Student Teacher (submits and revises reflections). Email verification and password reset are built in.

My role: testing

As Testing Lead, I built a structured test plan and guide so every role and workflow could be checked the same way before and after release. Testing covered login, permissions, reflection submission and revision, invitations, and feedback.

Inherited architecture

The previous team delivered the core architecture, database design, APIs, and reflection workflows. Our team chose to keep that stack rather than rebuild it, and focused on stability, deployment, and usability.

Stack

Django and Django REST Framework backend; React (JSX), Vite, and Tailwind frontend; Axios with JWT authentication; PostgreSQL on Render.

Deployment

Backend and frontend deployed on Render, with automatic redeploys from GitHub and a custom domain connected through DNS configuration.

What we learned

  • Confirm hosting and domain funding early. A funding delay pushed deployment back.
  • Set firm deadlines with testers. Feedback arrived slower than planned.
  • Plan extra time after launch. Several issues only showed up on the live site.
  • Read the previous team's documentation before changing inherited architecture.

Risks documented for future teams

Yearly domain renewal, hosting and database scaling as usage grows, dependency updates (Django, React, Vite, Axios, Tailwind), and possible new client requests such as analytics dashboards or a mobile app.

Live demo ↗ Hosted on a free tier — the first load can take up to ~50 seconds.

Problem

Coaches receive long, unstructured emails from recruits and had to copy the details into a spreadsheet by hand. The goal was to automate that step and keep every recruit in one sortable place.

Data flow

Coach forwards email → scheduled AWS Lambda job (Amazon EventBridge, every 10 minutes) reads the inbox via the Gmail API → GPT-3.5 Turbo extracts structured player data → records are inserted into PostgreSQL on AWS RDS → Flask API → React dashboard. Each coach only sees emails forwarded from their own account.

My role: frontend

Turned client requirements into the React interface: dashboard, player table, sidebar and navigation components, and the signup, login, and landing pages. Data reaches the UI through Axios calls to the Flask REST endpoints.

Authentication

Passwords are salted and hashed with bcrypt before storage. A forgot-password flow sends a reset link through SendGrid to a page where the user sets a new password.

Backend & infrastructure

Flask with SQLAlchemy, Docker Compose for local development, and Render for hosting the frontend and backend, with automatic redeploys from the deployment branch.

What the team delivered

  • Requirements analysis document
  • Calendar for recruit schedules
  • Two-way email recruiting system
  • iOS support via a PWA
  • Login fixes (duplicate accounts) and password reset

Known limitations & what I'd do next

  • No manual "parse now" button, so coaches wait up to 10 minutes for new recruits to appear.
  • Some emails get parsed more than once, creating duplicate players. The parser needs duplicate detection.
  • One shared inbox for all coaches is a bottleneck at scale. Splitting into multiple inboxes would fix it.
  • The athlete page was built but never connected to login or roles, due to a client-requested pause.
  • Backend unit tests were not passing at the end of the semester, and formal user testing was not done.
